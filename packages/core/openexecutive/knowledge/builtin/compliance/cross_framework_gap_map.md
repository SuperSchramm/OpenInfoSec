# Every Sector Has a Framework. None Specifies the Architecture.

A structural gap runs through every major U.S. critical-infrastructure compliance framework: each one mandates a security *outcome* without specifying the architecture required to achieve it. The same missing layer — a formally governed cloud boundary, and an AI governance specification for OT-adjacent systems — is absent from HIPAA, NERC CIP, the TSA Pipeline Security Directives, AWIA, and USCG NVIC 01-20 alike. Knowing exactly what each framework mandates versus what it silently assumes is what separates "we're compliant" from "we're actually protected" in a GRC conversation.

## The Gap, Framework by Framework

| Framework | Sector | What It Mandates | What It Leaves Unspecified |
|---|---|---|---|
| HIPAA Security Rule | Healthcare | Risk assessment, penetration testing, network segmentation, MFA, encryption — but only for systems handling ePHI | No technical architecture spec; no definition of *how* to segment; silent on cloud boundary governance and on AI as a security principal |
| NERC CIP (CIP-002 through CIP-014) | Electric Grid / Bulk Power System | Electronic Security Perimeter (ESP) definition, access controls, patch management, incident response, supply-chain risk (CIP-013) | No formal ESP specification for cloud-hosted systems interacting with BES assets; no governance for DERMS, cloud historians, or demand-response aggregators; no AI governance for grid-optimization AI |
| TSA Pipeline Security Directives (SD-02C and successors) | Oil & Gas / Pipeline | IT/OT network segmentation, access control, patching, continuous monitoring, incident response — the most prescriptive pipeline OT standard post-Colonial Pipeline | No cloud-boundary spec for cloud-hosted pipeline monitoring or remote SCADA access; no formal governance for vendor remote-access portals — the exact Colonial Pipeline attack vector |
| AWIA 2018 / EPA Risk Assessment Requirements | Water / Wastewater | Risk and resilience assessments every 5 years, emergency response plans | No mandatory technical cybersecurity standard for most systems; no segmentation requirement; no internet-exposed-PLC specification; no AI governance |
| USCG NVIC 01-20 / MTS Cybersecurity Final Rule | Maritime / Port Facilities | Cyber risk assessments in Facility Security Plans; references NIST SP 800-82; requires IT/OT identification; incident reporting via NVIC 02-24 | Still voluntary guidance in large part; the Final Rule adds minimum performance requirements but no cloud-boundary spec; no governance for satellite connectivity, cloud port-management systems, or AI cargo-optimization platforms |
| ISA/IEC 62443 | All OT sectors (international standard) | Zones and conduits, security levels (SL-1 through SL-4), component/system/program requirements — the most technically detailed OT security standard available | Written before cloud-hosted OT management was operationally common; no zone/conduit spec for cloud systems; no security-level assignment methodology for AI inference or agentic AI as a principal |
| NIST SP 800-82 Rev. 3 | All OT sectors (federal guidance) | Descriptive guidance aligned with the Purdue hierarchy — defense-in-depth, segmentation, IR, supply chain | Descriptive, not prescriptive; references Purdue Levels 0-5 but has no boundary architecture for cloud infrastructure; no AI governance framework |

## The Key Finding, and Why It's a GRC Problem Rather Than an IT One

Every framework in this table mandates that an organization protect its OT environment. **None of them formally specifies the boundary between that environment and the cloud-hosted systems now integral to running it.** That's not a gap any single control closes — it's a gap that survives a clean audit. An organization can pass a HIPAA risk assessment, hold a current SOC 2, and still have an ungoverned Citrix portal with no MFA sitting on the exact boundary that's absent from every framework's scope. Colonial Pipeline and Change Healthcare both entered through precisely that kind of unspecified interface.

## Applying This in an Audit-Prep or Gap-Analysis Conversation

1. **Map the compliance gap to the technical one before recommending a fix.** "HIPAA doesn't require MFA on this system" is true and also not the point — the point is HIPAA's silence on cloud-boundary architecture doesn't mean the boundary is safe, it means the framework never asked.
2. **Treat "unspecified" differently from "prohibited."** A framework leaving cloud-boundary governance unspecified is not license to skip it — it means the organization needs an internal architecture standard (see the Level 6 Cloud Tier framework) to fill a gap the regulator hasn't closed yet.
3. **Flag AI governance as a universal blind spot, not a sector-specific one.** Every framework in this table is silent on AI as a security principal. If a client has any Class 3 or Class 4 AI system (see the AI governance taxonomy) in scope, that's a gap no compliance framework currently tests for — which means an auditor won't catch it, but an incident will.
4. **Escalate architecture-level gaps to the CISO, not just the audit tracker.** A clean audit against a framework that doesn't specify the architecture is a real deliverable, but it is not evidence the underlying risk is mitigated — say so explicitly rather than letting the audit result read as the final word.
